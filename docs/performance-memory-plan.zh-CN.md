## 第一项源码优化：缩略图缓存

原实现最多按10000条计数，到限后整池清空；GUI查询和后台插入未统一同步，
同一缩略图尚在读取时，每次绘制都继续排任务。现在使用16MiB估算成本预算的
LRU，单条最低32KiB记账，普通条目最多512个；只淘汰冷条目，不清整个池。
同一键的并发未完成读取只保留一个，修改通知使旧结果作废并合并为一次重读。

所有缓存／排队状态有互斥保护，值先复制再解锁。后台任务不持有原始QObject
指针，只持有独立可关闭状态，完成信号回GUI；销毁后排队任务不发布结果。
不触碰笔记正文、保存队列、加密和锁定规则。缓存统计只含计数，不暴露身份或内容。

16MiB是估算记账预算，不是整个进程RSS硬上限；外部视图的共享QImage引用不由
缓存控制。单个异常超大缩略图按整份预算独占保留，避免丢质量或无限重新加载，
因此也不宣称超大单条的实际内存严格小于预算。正常索引保持原50像素缩略图规则。

必要检查：LRU／成本／并发／迟到结果12项、实际临时DB／GUI完成／重复读取／
更新／销毁10项，最终22／0。初次实际索引夹具错误地比较原64像素图，忽略原来
就有的50像素缩略图转换，一项失败保留；改为比较原索引实际字节／图像后通过。
不为此修改原索引或图片质量，也没有重跑不相关的完整客户端回归。

2000张50×50标准合成图独立进程比较：旧缓存持有20000000字节图像，新缓存
512条持有5120000字节，减少74.4%。进程footprint同时记录但不是整个App降幅；
2ms／1ms这样的小基准差值不推广成日常打开速度提升。500次实际重复查询只建
一次数据库读取的效果已由生产缓存和临时索引联验，不仅是独立原型。

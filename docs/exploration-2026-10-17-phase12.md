# 第十二轮：保留当前标签页与原生 Qt 对照

2026-10-17。继续内存归因，**只修改隔离测试／测试构建和记录，不改变正常 App 的渲染、保存、同步、编辑或数据策略**。不安装、不生成新的产品候选；已交付的 14.4.18、现用 14.4.17 和冻结的 14.4.16 保留。

## 本轮解决的测量缺口

此前每批关闭全部四页，不能直接代表日常使用。本轮增加一个始终保留的笔记，在普通 Qt 标签容器中依次打开四页、关闭四页并回到保留页；加载每页时先选中它，随后后台三页隐藏、当前页可见。宿主仍为 900×600 点，不启用真实账号、资料列表、同步或外部请求。

每批检查四页的原文／预期公式，关闭后确认视图和页面销毁，保留笔记仍可见且内容完整。后续对照额外检查每页内部 `QQuickWindow` 销毁及窗口数。保留页存在时进程树为 2（本进程＋保留页渲染器），最终主动关闭保留页后为 1，不能把正常保留的渲染器误算作泄漏。

原生 Qt 空白对照直接构造 `QWebEngineView` 和 `QWebEnginePage`，不使用 App 的网页／页面子类；实际断言其类型、没有 QWebChannel、DOM 中脚本数为零，且 `WizEditor`／`MathJax` 未定义。仍沿用相同的临时隔离 profile 和宿主，以减少无关变量；**它仍运行在测试二进制中，不冒充完全独立的 Qt 最小程序**。

## 结果

以下为每批关闭四个临时页一秒后，本进程系统 footprint 的首／末值（MiB），首批含暖机；开页次数不含那一篇保留笔记。不是整个 App 的长期使用或内存泄漏定论。

| 对照 | 临时页打开次数 | footprint 首／末 | 结论 |
| --- | ---: | ---: | --- |
| 保留数学笔记，默认 Metal | 120 | 230.80／1575.38 | 保留当前页仍增长 |
| 请求 Quick 图形资源释放 | 40 | 236.31／658.88 | 没有阻止增长 |
| 每批显式原生临时对象池 | 40 | 236.86／661.91 | 池释放后也仍增长 |
| 当前图形上下文等待 GPU 完成 | 40 | 234.53／661.61 | 没有阻止增长 |
| 当前图形上下文释放后端缓存 | 40 | 231.67／660.50 | 没有阻止增长 |
| 原生 Qt 空白控件，Metal | 40 | 226.22／651.61 | 不依赖 App 网页子类／编辑器即可复现 |
| App 空白控件，Metal | 40 | 225.69／659.33 | 与原生控件方向一致 |
| 原生 Qt 空白控件，软件后端 | 40 | 187.38／187.86 | 本轮未见相同持续增长 |

共 400 次临时页开关、346 条命名检查通过。所有数学组保留完整 Markdown 和每页 16 个公式；所有小组无外部请求，关闭后的页面和进程数量符合预期。后续对照关闭后原生窗口数稳定为 2，最终只剩宿主窗口；无四页绘图窗口不断存活的证据。

数学长测的 RSS 为 198.03→211.28 MiB，等十秒后约 202.88 MiB；但 footprint 等十秒后仍为 1515.56 MiB。原生空白 Metal 等十秒后约 606.08 MiB，软件对照约 186.81 MiB。**RSS 较平不能代表图形相关内存稳定。** 软件对照的 RSS 本身比 Metal 高，也不能拿这组数据承诺切换后端就能全面省内存。

对象池对照在池释放前／后分别取样，释放后首／末约 204.36／629.91 MiB，仍有增长。它未证明所有原生临时对象都无问题，只是否定“加一个批次对象池即可修复本次曲线”的方案。GPU 完成／后端缓存对照仅操作保留页的上下文，不声称枚举并排除了所有底层资源或驱动缓存。

## 不采用的修补与依据

- 不关闭产品硬件加速，不切换 OpenGL 或软件后端，不丢弃撤销历史、冻结／卸载用户笔记。
- 不把每次关页清理图形缓存、强制 GPU 同步或新增对象池加入正常 App：本轮无有效改善，且存在额外开销／兼容性边界。
- 使用的图形控制均局限于测试。Qt 的 [Quick 资源释放说明](https://doc.qt.io/qt-6.8/qquickwindow.html#releaseResources)指出其作用受渲染循环及持久设置影响；[QRhi 文档](https://doc.qt.io/qt-6/qrhi.html#finish)说明 GPU 等待会执行延后操作并提醒避免常规使用。QRhi 的兼容保证有限，因此额外封装在可选测试静态库中，不给普通构建加入该接口。
- 对照实际编译的是本机 Qt 6.11.3 SDK。在线文档显示版本为 6.8／6.12，仅用于理解 API 约束；不是相同版本实现的根因证明。通过 GitHub 插件请求 `qt/qtbase` 的 `v6.11.3` 源文件返回“无此 ref”，未拿另一个版本／主分支冒充精确源代码。

测试构建显式引用已在 WebEngine 依赖中的 QuickWidgets；可选 RHI 源只在受支持的 macOS／Qt 版本中编译，缺失支持则拒绝对应诊断模式。正常构建和已交付二进制不变。原型中曾修正 CMake 链接签名混用及源文件编译定义的目录作用域；最终构建结果以下方回归记录为准。

## 当前判断与下一步

现有证据把优先排查范围缩到 Qt 原生网页显示／Metal 交互路径，而不是数学解析、Markdown 源码或页面对象未销毁。但尚无分配堆栈、具体根因代码行或跨机器／跨 Qt 版本比较，不能宣称已经修复、确定是驱动泄漏，或断言日常 App 必然呈现同样曲线。

下一步应提炼完全独立的 Qt 最小复现，并核对同机／其他 Qt 或系统环境的结果，再选择最小风险方案。不能为了让数字下降，把没有效果或成本未验证的实验默认启用。本轮未解决 PDF 引用纵向偏移，也不更改其导出路线。

开发构建仍使用精确隔离入口 `--editor-memory-probe`。保留标签页须同时明确设置 `WIZNOTE_MEMORY_VISIBLE_COCOA=1`、`WIZNOTE_MEMORY_SHARED_HOST=1` 和 `WIZNOTE_MEMORY_KEEP_NOTE=1`；会显示合成窗口并自行结束。

额外诊断参数仅适用于开发测试，不应写入正式 App 启动设置：

- `WIZNOTE_MEMORY_RELEASE_GRAPHICS=1`：Quick 资源释放请求。
- `WIZNOTE_MEMORY_BATCH_POOL=1`：每批原生对象池与释放后采样。
- `WIZNOTE_MEMORY_RHI_CONTROL=finish` 或 `cache`：保留页上下文的 GPU 等待／后端缓存对照。
- `WIZNOTE_MEMORY_STOCK_VIEW=1`：须同时设置 `WIZNOTE_MEMORY_EMPTY_CONTROL=1`，构造无 App 网页子类、桥接和编辑器脚本的 Qt 空白控件。
- `QT_QUICK_BACKEND=software`：独立软件后端对照，不是产品建议设置。

汇总器区分保留页的预期进程数，并拒绝缺少最终关闭、对象池采样或存在多余子进程的日志。

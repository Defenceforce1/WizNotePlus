## PDF 实测

新增本地合成 Markdown 夹具生成器，使用当前原编辑器、科学数学 CSS 和 **MathJax 2.7.6**，包含定理／定义引用、一个显式编号公式及公式引用。原探针继续调用实际 Qt **6.11.3** 的 `QWebEnginePage::printToPdf`，没有换成外部浏览器、LaTeX、Pandoc 或后处理。

普通样本和刻意靠近分页边缘样本各输出 5 mm、20 mm、真实可见标题锚点三份，共 **6 份**。全部确认原 Markdown、HTML、修改状态保持一致，两个数学块、三个 MathJax 对象、零公式错误及零外部页面请求。原夹具等待 `MathJax.Hub.Queue` 后再等待字体与两帧绘制，不把 MathJax 3／4 的 API 套在版本 2 上。

第一次误用精简包未包含的 offscreen 平台插件而启动失败，没有输出 PDF；使用该自包含包实际包含的 Cocoa 插件后正常完成。父进程库、插件、helper 和资源取自同一现存候选运行库，未关闭沙盒或读取账号。

新增只读 PDF 审计工具，检查内部 GoTo 名称是否有确切命名目的地，区分直接数组、外部 URI 及 file-fragment URI；存在可解码候选不等于 PDF 名称实际可解析。它不修改 PDF，也明确说明**可解析不等于位置准确**。

结果：

- 六份 PDF 中定理／定义及普通标题的目标均在正确页；但纵向偏移依然存在，且受边距、布局／缩放及目标类型影响，不能统一补一个固定距离。
- 普通样本定理标题与目标差值约为 **-7.77 pt（5 mm）／-53.19 pt（20 mm）**；移到真实标题元素后约 **-18.27 pt**。这不是有效通用修复。这里负值表示命名落点位于标题墨迹下方，字体墨迹与容器顶边本来也不完全相同。
- 公式引用均指向缺失的 `mjx-eqn-eq%3Apdf-eq` 命名目的地。等待公式完成并没有自动补上 PDF 目标；真实标题变体也未修复公式引用。
- 当前 DOM 记录覆盖普通 HTML anchor，SVG 中的引用／目标还须继续单独核对，不能把 HTML 检查当作最终 PDF 完整性验收。

因此用户此前转述分析中“定理／定义坐标正常”的判断不能作为验收依据。用户 PDF 的具体标题、目标、坐标和页面内容不在此公开记录。

## 是否升级组件

优先评估 Qt／WebEngine 的新维护版本，但只在独立环境用相同夹具比较；没有证据表明升级必然修复本次坐标问题。Qt 官方已发布 [Qt 6.12](https://www.qt.io/blog/qt-6.12-released)，且 [WebEngine 独立版本说明](https://www.qt.io/blog/qt-webengine-will-release-separate)明确首个 6.140 仍基于 Chromium 140，因此不是看到新版本号就得到另一代打印引擎。

MathJax 2.7.6 较老，可研究维护更新／新引擎对照；但 [官方迁移说明](https://docs.mathjax.org/en/stable/upgrading/v2.html)明确 v2 到新版不是直接替换，Hub／Queue、启动、渲染和 DOM 均有变化。现有 label／ref／eqref、数学 CSS、旧笔记往返必须独立验收，暂不改变默认。Markdown 解析器也不因 PDF 坐标问题而整体替换。

下一步优先核对打印缩放与命名目标坐标转换，以及 SVG 公式目标导出；A／B 方案继续使用原 HTML／公式和同一导出路线。没有对正式 PDF 加后处理、书签或强制坐标偏移，也没有承诺组件升级即可解决。

# 列表空标签查询优化与原生内存归因

本阶段实现一个确认有效的列表优化，并继续核实239留下的原生内存差异。
列表查询次数已减少；原生内存风险尚未消除，不把诊断工具完善写成产品降RAM。
没有新包、组件升级或真实资料操作。

## 列表成功空值不再反复查库

笔记列表在排序／信息刷新时获取标签。原实现用空串判断“尚未加载”，成功
查到没有标签仍会再次查询。现在使用既有QString的null状态代表未加载，用
非null空串代表成功的空结果，不增加每条列表字段或全局缓存。

只有查询成功才写缓存，沿用原来的显示名转换和分隔符。失败保留未加载状态
供下次重试；原有clear／reload及隐藏根目录的失效语义保持。源笔记、标签
存储和排序规则不改。

真实生产列表对象／数据库通过独立合成入口测试，结果如下。所有数据位于
临时目录，SQLite trace只计该连接的标签SELECT，不启动普通主程序。

| 场景 | 原实现查询次数 | 新实现查询次数 |
| --- | ---: | ---: |
| 无标签连续获取500次 | 500 | 1 |
| 重载后再获取500次 | 501 | 1 |
| 隐藏根目录返回后获取500次 | 500 | 1 |
| 删除最后标签并重载后获取500次 | 501 | 1 |

正标签显示／已有正缓存、失败两次后恢复查询均通过。最终优化组22项，另旧
21项对照单列；真实manager修改通知到item.reload的路径通过，但不是整个
主窗口／云同步验收。500次空值获取一次观测6.15→0.058ms，仅供局部参考，
不是稳定多次基准或整个App速度倍数。减少重复SELECT和临时SQL／标签数组
准备，不等同于测得整个进程内存下降。

## 原生内存差异仍存在

在同一诊断程序中分别使用238与239自有JS，仍是每组同一临时持久profile、
6000段／128公式／2引用开读、回编、关闭八次。新增自有任务VM记账字段，并
在profile保持存活时观察10／30／60秒；两组118项、16次关闭通过，页面／
控件／Quick窗口／profile子对象均归零。没有强制回收或改生产profile所有权。

| 空闲60秒 主进程指标 MiB | 238源码 | 239源码 |
| --- | ---: | ---: |
| footprint | 62.16 | 87.13 |
| malloc在用 | 19.82 | 19.81 |
| VM内部页 | 51.31 | 75.83 |
| VM可复用页 | 25.34 | 0.19 |
| 压缩内存 | 0 | 0 |
| 图形footprint记账 | 3.69 | 3.95 |

两组10至60秒数值基本稳定。差异主要对应内部／可复用页状态，不由等量的
malloc活动对象、压缩量或图形记账增量解释；“分配器或内部页驻留高水位”是
线索而非已证明原因，仍未定位具体持有者。不能宣称常驻内存下降、泄漏被
排除或增加等待就会解决。诊断的新字段／定时观察仅属于测试目标，不进入
普通生产App。

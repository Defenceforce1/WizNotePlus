# 主程序兼容优先探索：第一轮证据与实施顺序

日期：2026-10-17。基线：用户确认正常的 **14.4.16**。本文保留四阶段的证据演进，最新状态见第四阶段：已完整编译工作区开发候选并通过 13 组回归。**没有安装／交付新版本，或操作真实笔记、凭据、云端**。原始编辑器、MathJax、PDF 基本内容链路、资料格式和已安装包不变；当前候选含渲染、PDF 文件安全及线程修正，不代表全部计划完成。

本轮新增的开发测试和文档不是生产依赖。独立剪藏器不在范围内。固定回退物见 [回退说明](rollback-14.4.16.md)。

术语说明：下文实验中的“原版／原实现”指当前 **14.4.16 基线**，不是声称上游官方原版存在同样问题。R1、R2、R4 位于本次适配新增的数学装饰层，应先修好这一层，不能归咎于用户笔记格式、上游旧版或单纯的引擎版本年龄。

## 结论

不建议先整体更换编辑器或公式引擎。已有几项更小、更直接的改进机会：

1. **优先消除引用反复装饰产生的空文本节点**，再做查找结构与重复渲染优化。
2. **引用识别必须尊重完整公式边界**，包括跨行内元素的公式，不能只补一个正则。
3. **屏幕定位突出可不改原文、不改排版实现**；原型已检查源内容一致且打印时不显示。
4. **PDF 定位要分开处理锚点位置和打印坐标**；仅改定理 CSS 或挪动 ID 无法证明完全修复。
5. **加载／保存队列及页面销毁后的回调值得优先做原生稳定性验证**。不能把浏览器实验当成这些风险已经在 App 中复现。

## 一、引用、Markdown 与数学渲染

### R1：引用反复装饰会累积空文本节点——已复现，优先级高

位置：`share/files/wizeditor/editorHelper.js`，`WizApplyMathEnvironments` 替换引用文本的逻辑。

原实现不论前后文本是否为空，都向 fragment 插入文本节点。恢复链接原文后再装饰，每个引用每轮又增加两个空节点。保存／读取源码的保护包装也会清除并重新装饰，因此不需要用户真的编辑原文就能触发。

独立 DOM 对照，每页从相同、未装饰的 HTML 开始：

| 引用数 | 重建次数 | 原版新增文本节点 | 跳过空文本原型新增节点 |
| --- | --- | --- | --- |
| 500 | 30 | 30,000 | 0 |
| 1,500 | 30 | 90,000 | 0 |

两种路径的序列化内容一致。500 引用样本在一次记录中，原版 30 次装饰合计约 586 ms，跳过空节点约 173 ms；这些是单机局部 DOM 微基准，**不是 App 整体提速倍数**，也不是严格控制所有热身／系统负载因素的性能结论。

完整旧阅读器的 Chrome 实验中，原型通过原文一致性、原有编辑／阅读切换、原始公式与代码检查。实际 Qt 隔离 DOM 里，100 个引用重建 20 次，原版新增 4,000 个文本节点，原型新增 0，序列化一致。完整 Qt 候选阅读器集成和发行包仍需验证，不能把原型嵌入测试页等同于已升级应用。

### R2：公式边界存在误识别——DOM 扫描复现，需完整引擎验证

现有保护只对普通分支检查 `$` 的奇偶，无法完整保护 `\(...\)`、`\[...\]`、`$$...$$`；公式若跨 `<em>`／`<span>` 等节点，单个文本节点甚至看不到开始分隔符。

20 个扫描用例中，原版 7 个与“只装饰普通文字／完整独立行内引用”的约束不符。仅加文本分隔符状态的原型修复其中 5 个，但漏掉跨节点的 2 个；按同一段落的可用文本构建上下文的第二原型通过全部 20 个。

实际 Qt 的隔离 DOM 补充样本也复现了复合括号公式、展示公式和跨行内元素公式三种误识别，普通文字引用正常；这不是只在新版 Chrome 中出现的现象。

**不能直接把第二原型当成完整 TeX 解析器交付**：仍需扩大到嵌套内容、转义、分段公式及原 MathJax 预处理顺序的集成测试。不要改变既有公式标签／编号表，也不要把数学块标签硬塞进公式引擎标签表。

### R3：临时定位突出可行——原型通过，未交付

点击数学引用后，使用编辑器认可的临时样式在目标外侧短时显示轮廓，不增添目标属性、正文 UI、字号或间距。使用 `@media screen`，不参与打印，不创建另一套打印 CSS。

实测源码／序列化 HTML 与原来一致，打印媒体下没有轮廓，原有本页跳转和 URL 保持不变。短篇末尾不能总把目标滚到视口最顶，是滚动边界，不等同于定位失败。长文样本中原版目标距视口顶部约 0.19 px，原型屏幕滚动留白后约 24.19 px，滚动距离超过 4,000 px；源码、HTML 与未修改状态保持一致。缩放、嵌套滚动容器和关闭／换页时定时器清理仍需验证，浏览器结果不替代完整 Qt 集成。

### R4：手写编号的 HTML 清理有浏览器差异——已缩小原因，低于内容错误优先级

在 Chrome 155 中，CSSOM 设置计数器后直接删除 style 属性，可能延迟生成 `style=""`。32 个混合环境样本中 22 个严格 HTML 字节对比不同，差异定位到这个空属性；不是正文丢失。删除前读取 style 属性以刷新待序列化值的原型，32 个都恢复精确一致。

实际 Qt 引擎的手写编号样本也出现这个空属性，读取后再删除的原型恢复精确一致。不是仅新版浏览器特有的问题，但尚未将原型纳入完整候选。原 Markdown 内容往返测试仍通过；后续应把所有“未修改笔记不被标成已修改”路径纳入检查。

### R5：原公式引擎仍可满足当前核心需求

使用原资源的完整阅读器样本完成了 24 个展示公式；另一组完成 11 个公式对象，包含黑板体、运算符、多行对齐、分段函数、矩阵、积分、求和、公式 label／eqref、Markdown 表格及独立定义引用，没有发现 MathJax 错误节点，源码保持一致，代码围栏内的命令未被装饰。

原编辑／阅读往返 5 轮保持源码和只读装饰规则。一轮包含模式切换的探索曾出现 `Cannot read properties of null (reading 'Callback')`；单独复查及进一步 15 次往返未重现，不能删掉失败记录或宣称问题已解决。压缩编辑器确有动态重置 `MathJax = null` 的路径，需要继续检查异步加载代际／关闭时序，不能仅因引擎老就直接升级。

## 二、PDF 导出

### P1：页边距单位没有传入布局——源码确认

`WizDocumentWebView::saveAsPDF` 读取 `printMarginUnit()`，却用默认单位构造 `QPageLayout`。复核官方头文件、文档和实际 Qt 6.11.3 库确认：默认单位是 **Point（点）**，不是毫米。界面有毫米／点／英寸／Pica／Didot／Cicero 六种，保存的是 0–5 的选项索引；这个顺序与当前 Qt 单位枚举相同。

**更正此前分析**：初稿曾将默认单位误记为毫米，相关例子不正确。原生布局探针的首次断言因此失败 1 项；这是测试预期错误，不是新发现的 Qt 故障。实测设置 5 毫米变为 5 点，约 **1.76 mm**；72 点仍正确为 **25.4 mm**；1 英寸变为 1 点，约 **0.35 mm**。显式传入所选单位的对照才分别是 5、25.4、25.4 mm。Didot／Cicero 对照也已覆盖。该探针只构造 Qt 布局，不生成 PDF，不证明目标坐标修复。

这是独立缺项，**不能据此断言它就是此前所有 PDF 跳转偏移的原因**。恢复正确单位会使默认的 5 毫米设置从此前约 1.76 mm 实际边距变为 5 mm，可能改变分页，必须另行比较；不能声称毫米路径不受影响。后续使用明确单位及有效范围检查，保留原入口和同一份 CSS。依据：[Qt QPageLayout 构造及单位](https://doc.qt.io/qt-6.11/qpagelayout.html)。

### P2：导出前删除旧文件，缺少完成反馈——源码确认

同一路径在异步打印前已删除，且该路径未处理 `pdfPrintingFinished`。如果打印失败，用户可能失去原有同名 PDF，也得不到可靠结果提示。未发现显式等待当前 MathJax／图像渲染完成的门槛。

建议保留同一 `printToPdf` 内容链路，完成后检查结果，再原子替换目标文件；不需要 PDFKit 重写、不需要新增打印窗口，也不改变笔记格式。失败时旧文件必须保留，页面关闭时不得再访问失效对象。

### P3：锚点与打印坐标的对照——浏览器复现，Qt 待验证

生成合成多页 PDF，读取真实命名目标坐标，并和页面文字位置比较。下表差值为“可见标题文字上沿 − PDF 目标上沿”，包含字号墨迹位置／块内边距，不把全部差值都当成同一种错误。

| 目标 | 5 mm 页边距 | 20 mm 页边距 |
| --- | --- | --- |
| 定理／定义块 | 27.75 pt | 69.75 pt |
| 普通标题锚点（对照） | 15.75 pt | 57.75 pt |

目标页均正确；两类目标随页边距变化都增加 42 pt，说明此试验的偏移不只来自数学块 CSS。把数学块 ID 移到可见标题的诊断原型，可把 5 mm 差值降至 17.25 pt，**仍未消除打印边距相关部分**。

已查看目标页的实际渲染画面，公式／正文排版在这些样本中正常。旧版“只显示原始隐藏标题”试验不能解决坐标问题；最初原始 HTML 对照夹具还触发原阅读器规范化，导致原文一致性断言失败，已改成可撤销的 DOM 对照插入并通过，原失败记录保留。

下一步：必须用同样夹具和设置走 Qt 的实际 PDF 输出，并测试 0／5／20 mm、不同缩放、跨页标题、长环境和双向链接。没有确认 Qt 坐标语义前，不加入固定像素偏移补丁，不恢复已撤回的 PDF 后处理路线。

已尝试只对隔离原生测试页调用调试协议打印，但此 Qt 引擎未暴露 `Page.printToPDF`（返回 method not found），没有生成原生 PDF。这个调试接口缺失**不代表 App 的另存为 PDF 失效**；实际导出需要 Qt C++ 的 `printToPdf` 路线，须在恢复编译环境后的定向夹具中验证。

## 三、原生稳定性与加载／保存

没有操作用户资料。现有包的 25 项隔离保存／退出测试通过，说明其既有覆盖范围正常；完整 saver／loader／视图生命周期故障还没有定向复现。C1、C3 已补充原生 Qt 协议小测试，范围明确如下，不把它或模型当成真实用户笔记崩溃重现。

| 编号 | 位置与观察 | 风险及下一步 |
| --- | --- | --- |
| C1 | `DocumentLoaderSaver.cpp/.h`：队列为空的判断、等待注册使用不同的锁；通知不是持久信号 | 任务／停止通知可落在检查和等待之间。模型在 6 种任务顺序中找到 1 个任务漏通知反例；停止路径也有反例。原样等待类的原生 Qt 小测试再次确认这两种通知丢失，单锁谓词参考实现正常。需进一步验证完整保存队列排空及退出语义，不以强退解决。 |
| C2 | 同一加载器只存一个当前 GUID；所有笔记页共享该加载器 | 多个不同页的请求可在消费者取走前互相覆盖。模型明确显示 A、B 先后发布后只剩 B；App 是否补发需原生验证。考虑按请求者／代际区分，而非全局只保留最后一项。 |
| C3 | `WizMainWindow::createDocumentView` 每页向共享 loader 的 `loadFailed` 加一个无接收者上下文的 lambda，直接显示对话框 | 旧连接不随该页自动失效，还缺少所需的 GUI 线程／笔记过滤约束。原生 Qt 小测试确认这种无上下文回调跟随工作线程执行，有应用接收者的队列连接则正确回到主线程。未代测实际错误弹窗；需加入过滤和防重复检查。 |
| C4 | `WizDocumentWebView` 多处异步 JavaScript 回调捕获裸 `this` 并读写 view／page；重载回调还用了无上下文的 `singleShot` | 页面删除或切换时需要对象保护、请求代际以及无效结果分支；保存回调必须恰好完成一次，不可只是静默不返回。 |
| C5 | `WizDocumentView::waitForThread` 对状态检查线程只调用 quit；等待的是另一个同步线程，析构直接删除 checker | 需要核对实际任务结束与 QObject 销毁线程，避免“已请求退出”被当成“线程已结束”。不可破坏现有保存优先／退出取消语义。 |
| C6 | 编辑状态同步线程的 `QNetworkAccessManager` 无 parent，以 `QPointer` 保存，未见对应销毁 | 是所有权清理项，尤其是群组路径；QPointer 不拥有对象。不能因此删除既有群组资料或同步。 |
| C7 | `onEditorLoadFinished` 给 runJavaScript 传入 async IIFE，并立刻通知插件；Qt 不把返回的 Promise 当成待完成的初始化结果 | 需要显式编辑器就绪通知及当前笔记／加载代际校验。不能以网页 loadFinished 或 JavaScript 求值回调代替公式、图片和桥接初始化全部就绪。 |

依据 Qt 6.11 文档：等待中的线程才能接收条件通知；JavaScript 回调可能在 page 析构期间执行，此时不能使用 page/view；运行中的 QThread 不可直接删除。源码中的上述路径应分别覆盖，不将所有退出延迟归为同一问题。

- [QThread 生命周期](https://doc.qt.io/qt-6.11/qthread.html)

## 四、内存与资源策略

### 已观察到的良好行为

同一个隔离浏览器页在短公式笔记和 24 公式笔记间切换 6 次，每次主动 GC 后：短页 DOM 节点／事件监听器稳定为 454／125，公式页稳定为 2,593／235；清空为 blank 后为 4／0，JS 使用量约从 7 MB 回落至 0.9 MB。

这轮没有看到“整个页面被永久保留”的证据。**不抵消 R1：R1 是同一篇笔记反复装饰的节点增长，导航后可以释放；两种测试检验的是不同生命周期。**

另测 1／3／6 个独立公式页，记录了浏览器进程组 RSS。RSS 相加会重复计入共享页面，且浏览器有缓存、进程预热和异步释放；这些数字不能当成主 App 的实际物理内存，也不能用关闭后的剩余 RSS 直接证明泄漏。

### 值得原生量化的点

- 每个文档视图都立即创建隐藏的评论网页、独立 profile 及状态线程。可评估按需初始化，保留当前功能接口，不删除既有内容／群组能力。
- 文本装饰的逐条数组 find 可以改为本轮局部 Map。原型结果一致，但应先修节点增长，再比较稳定状态性能，不用病态积累后的结果夸大 Map 收益。
- 后台只读页面可研究 Qt 推荐生命周期状态；不能自动丢弃未保存编辑页、撤销历史、正在排版／输出 PDF 的页面。Qt 已自动管理 view 的页面可见性，不能把“没有自定义冻结代码”说成所有后台页面一直可见。
- 源码初看评论控件由主窗口作 parent，但随后会被 splitter 接管，因此**没有把这点误报为确定的孤儿控件泄漏**。

### 原模式切换中的拼写属性

新增原生循环最先暴露两个测试约束问题：初稿在同一 JS 任务中立即 on／off，没有等真实编辑回调；严格 HTML／DOM 相等又包含原引擎每次重建的随机目录 ID 和格式空白。已改为匹配生产回调顺序，分别检查**完全一致的 Markdown、公式 TeX、环境编号／目标／引用、编辑中的未修改状态和保存属性**，不抹平或改写用户文字。

同时确实复现了正文 spellcheck=false 残留：旧引擎会替换 body，原属性记录不能仅跟随一个节点。候选在本页面保存原始正文属性，小型 WeakMap 跟踪其他节点，模式转换前仅恢复临时拼写属性和数学装饰；不清理用户样式或代码控件。CodeMirror 的隐藏输入合法带 spellcheck=false，测试只禁止正文控制属性泄漏，不删除该代码功能。新增反复引擎重置／序列化检查通过。

最终 15 轮 Qt 切换：Markdown 原文、数学及编号引用一致，临时属性不留入正文；原 HTML 字节相等轮数为 0，因为旧引擎会重建预览目录 ID／排版空白，**不声称整个预览 HTML 字节永远相同**。各轮失败证据保留在本机，未上传原始日志。部分 offscreen 测试有 Chromium GPU context-lost／Skia 警告；不据此宣称真实窗口图形路径已验证或被修复。

### 退出：3 秒启动，10 秒无进展

用户先要求 5 秒改为 3 秒，随后明确澄清：3 秒仅限连接／启动，同步开始后应继续到完成。用户再把无进展时限从提议的 30 秒改为 **10 秒**。生产候选已按最终规则实现：

1. 先确认本地保存成功；不把本地保存缩为 3 秒或 10 秒，失败不静默退出。
2. 处理已有同步，再发起一次最后完整同步；连接／启动等待 3 秒，不自动循环重试。
3. 开始后持续等待。实际字节传输、成功响应及同步进度变化刷新无进展计时；普通重复日志、零字节心跳或其他线程请求不能刷新它。
4. 完成（包括失败）、断网导致的请求失败，或连续 10 秒无进展后结束等待，保留未上传本地内容供下次同步。原退出清理／取消和安全 TLS 不变。

活动观察器仅属于当前工作线程，作用域结束恢复，不保留网址、账号或载荷。另修复同步线程开始等待前丢失唤醒、最多睡满 3 秒才处理请求的问题。原生离线两次尝试均在启动时限内完成；真实本机慢速 HTTP 夹具传输超过 3 秒仍完整接收 8 字节；合成单调时钟覆盖持续两分钟的有进展同步，以及精确 10 秒无进展边界。本机测试不用真实服务器／账号，尚未手动验证完整主窗口退出时的联网界面。
